## 失败分类口径（先定义再统计，避免事后硬凑）

- **env_setup**：依赖/路径/权限问题，agent 未开始解题就失败
- **tool_misuse**：工具调用参数错、循环调用、误读输出
- **logic_error**：理解了任务但业务语义实现错误（最有价值的 SFT/RL 信号）
- **gaming**：尝试绕过验收（改测试、硬编码、特判）——单独记录手法
- **timeout/resource**：超时或超资源预算

## 服务层指标（v2：接入 vLLM/SGLang 后填完）

> 这一节把「推理服务」本身变成可量化证据，回答 JD 隐性要求的并发/长上下文/稳定性。
> 由 `serving/rollout_manager.py` 在阶梯并发压测时直接产出。

| 指标 | 含义 | 面试讲法 |
|---|---|---|
| 并发拐点（p95 延迟突增处） | 单卡能稳定承载的并发 rollout 数 | 「我把 --max-num-seqs 从 64 提到 256，p95 在 192 处拐点」 |
| tokens/rollout 分布 | 轨迹长度分布 | 长轨迹占比 = 长上下文压力 |
| 长上下文占比（>20k tok） | 触发滑动摘要的比例 | 证明长 horizon 任务真的被覆盖 |
| 失败重试率 / OOM 次数 | 稳定性 | 断点续跑 + 健康检查后失败率从 X 降到 Y |
| prefix cache hit rate | 成本/吞吐（SGLang RadixAttention） | 共享系统前缀带来的吞吐增益 |

**结论模板**：「在 AutoDL 单卡上自托管 Qwen2.5-Coder-7B，并发 N 条 rollout 压测，
吞吐量 M tok/s，p95 延迟 Xs，长上下文轨迹占比 Y%，期间 OOM 0 次——
这说明我能端到端把 RL 数据生产跑起来，而不只是设计任务。」
